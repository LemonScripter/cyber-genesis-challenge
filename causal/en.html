What can the confined party do?

An anatomical and causal answer to the SolarWinds, CrowdStrike and runtime-formal-verification objections — with measured kernel verdicts, not assertions.

„...The SolarWinds update was validly signed, and the backdoor made ordinary API calls with ordinary privileges. What would kernel-level monitoring see? Logically correct instructions that fit the operating model. The problem is not the correctness of the instructions but the intent — and intent cannot be verified mathematically at runtime...”

— A well-founded industry doubt
How to read this — which rung, on which platform The argument below concerns DCC Ring 0: eBPF LSM programs running inside the kernel. This rung requires Linux (CONFIG_BPF_LSM=y, BTF, its own kernel — it does not work in a container). Where it is absent, the portable software rungs apply, with a weaker guarantee. The difference is marked throughout:
  • Level 1 · WASM/WASI — platform-independent, but only for guest code compiled to WASM. Denial is construction: a link error.
  • Level 2 · Ring 0 (eBPF LSM) — Linux, kernel ≥ 6.1. Writes, reads, exec and network are all decided at kernel hooks and inherited across fork. Starts in LOG-ONLY; blocking mode is a deliberate, separate step.
  • Level 3 · Hook / interpreter — Windows, macOS, Linux. Where no kernel rung exists, tool-call mediation and language chokepoints apply: recognition-based, soft containment.

Intent vs. touch

The objection is exactly right about conventional EDR and antivirus: deciding intent at runtime, over Turing-complete code, really is mathematically undecidable.

MetaSpace.Bio abandons the intent question. It does not ask what the update wants to do, but what it touches.

  • We do not judge the instruction: the question is not whether the instruction is „correct”, but whether the resource it wants to touch (a file or a network target) is part of the state space declared in the .bio. Unlike intent, that question is decidable.
  • The chokepoint sits at the causal chain Linux · Ring 0: a protected effect requires a valid, time-boxed grant. A program cannot issue one to itself: the token_map is frozen — user space, including root, cannot write it. A process that starts on its own has no grant, so it does not write. Measured 2026-08-07, in blocking mode: without a grant EPERM · with a fresh grant the write succeeds · with an expired one EXPIRED. The original design used a physical keystroke as the root; measured, that tracepoint does not exist on a modern kernel, so the root became an authenticated request.
  • Egress goes through the same gate Linux · Ring 0: the socket_connect and socket_sendmsg hooks judge outbound traffic from the same chain. sendmsg had to be added because, measured, sendto() — connectionless UDP, e.g. DNS-based exfiltration — walked out even with the network guard switched on. ⚠ The network guard ships disabled.
  • Inheritance cannot be shed Linux · Ring 0: if the update spawns a child (sh, python), dcc_fork_inherit carries the causal state over. The LSM hook is mandatory in the kernel — unbypassable from Ring 3.
  • Deletion and renaming are state changes too Linux · Ring 0: measured, the file_permission hook saw two of 13 ordinary file operations — unlink, rename, truncate and mmap writes went past it. Ransomware that encrypts by renaming never met the defence. Eleven further hooks were attached; the ratio is now 16/17.
Enforcement is a deliberate switch Every eBPF program starts in LOG-ONLY (the blocking toggle defaults to 0), and blocking mode is enabled only after the interference test — plus there is an emergency-bypass map should a service enter a blocking loop. This is deliberate rollout discipline (observe first, deny later), but it means „the kernel refuses” is true of blocking mode, not of the default state.

Who verifies the verifier?

The CrowdStrike outage is the perfect example of a closed-source, proprietary, third-party kernel driver running in Ring 0 introducing instability or supply-chain risk.

The structure of MetaSpace.Bio structurally eliminates the risk that originates in Ring 0 — but it answers only part of the second half of „who verifies the verifier?” today:

  • No kernel driver of our own Linux · Ring 0: DCC loads no third-party module. It runs as eBPF, which the kernel's own verifier checks statically before load: bounded loops, no free pointer arithmetic. It cannot panic the kernel — precisely the failure class behind the CrowdStrike outage.
  • User-space isolation Level 1: the WASM/WASI execution mode runs purely in user space with zero Ring 0 access. A fault in a WASM runtime can at most stop its own process; it cannot blue-screen the operating system.
  • Privilege-separated authority Linux · Ring 0: the application does not mint the grant. The token_map is frozen (bpf_map_freeze): user space, including root, cannot write it directly — issuance happens inside the kernel and can only be triggered with CAP_BPF. The application may ask over a unix socket with a signed request; the authority does not believe the identifier in the request but asks the kernel who the caller is (SO_PEERCRED). Measured: a corrupted signature · a replayed request · a request in another process's name · an over-long window — all rejected.
How far the answer reaches The closure above holds against an unprivileged attacker — where it is strong, and that is the real SolarWinds/ransomware class. What we do not claim: that it holds against a party that is already root. bpftool prog detach / unload is a deliberate rollback path, so root can disable the defence by hand — the root of trust remains the protection of root access. Two attack tests aimed at this are deliberately deferred and have never run: user namespace + CAP_BPF map tampering, and verifier bypass via BTF type confusion. It also remains open that the comm-based allowlist can be spoofed with prctl(PR_SET_NAME) — it should be inode-based instead.

Verification amortization

Proving the 10,000 lines of the seL4 microkernel really did take a decade, because the aim was the correctness of the entire Turing-complete code. MetaSpace.Bio does not verify arbitrary third-party code at runtime.

The core of the technology is verification amortization:

  • Turing-incomplete constitution (.bio): the .bio language that declares the rules is deliberately Turing-incomplete (no loops, no recursion). The state space is therefore finite and exhaustively explorable.
  • Z3 SMT solver: the constitution's correctness and consistency are proven offline, before execution, by Z3 (on the order of 30 ms).
  • O(1) runtime evaluation: at runtime the kernel proves no mathematics. It compares a precompiled, static ruleset against the parameters of the call.
What the proof covers, and what it assumes The Z3 result proves properties of the decision logic. The theorem's premises include an unproven lemma: every protected effect reaches a hook. That was an assumption, and measuring it is exactly what produced the coverage finding above — two of thirteen. Hook coverage is finite and closable; it is not a matter of belief.

Updatability vs. the fence

A system that cannot be patched quickly stays defenceless once a vulnerability appears. „Updatable only with physical access” would be a genuine operational risk at the level of software code. MetaSpace.Bio therefore separates the software code from the security fence (.bio).

  • Automatic code updates: the code of SolarWinds, or any program, may update remotely and automatically, even in the field.
  • An inviolable fence: because the membrane boundary (.bio) is static and separate, a newly arriving version brings its zero-day inside the existing fence.
  • Physical root of trust: only changing or disabling the security profile requires higher-level (local or physical) approval, so a remote party cannot dismantle the defence while legitimate patches run freely.
Where the argument reverses — the root of trust is root access The fence is inviolable because changing it needs a different privilege than running the protected program: loading rules requires CAP_BPF/root, the program itself is Ring 3. A remote attacker cannot dismantle the fence — unless they obtain root. DCC sharpens that distinction; it does not remove it.
